# ESP32 UI Limiter

## 1. Purpose

This skill acts as a resource and compatibility limiter
for UI UX Pro Max.

UI UX Pro Max may generate sophisticated designs, but
all generated interfaces must remain suitable for the
HatchAI ESP32 embedded web server.

The goal is to achieve:

- Modern, attractive UI
- Responsive layouts
- Lightweight frontend assets
- Low ESP32 memory overhead
- Efficient HTTP communication
- Smooth browser performance
- Reliable incubator monitoring
- Minimal interference with firmware control

IMPORTANT:

UI quality must never compromise incubator safety,
control-loop responsiveness, or device reliability.

---

## 2. Skill Priority

When UI UX Pro Max and this skill are both active:

1. Preserve HatchAI functionality.
2. Preserve hardware safety.
3. Follow ESP32 memory and performance constraints.
4. Maintain API compatibility.
5. Apply UI UX Pro Max design recommendations.
6. Add visual enhancements only when affordable.

If a UI UX Pro Max recommendation conflicts with
these constraints, simplify or reject it.

This skill overrides visual design preferences
when resource or compatibility conflicts occur.

---

## 3. Technology Restrictions

ALLOWED:

- HTML5
- CSS3
- Vanilla JavaScript
- CSS Grid
- CSS Flexbox
- SVG icons
- CSS transitions
- HTML Canvas
- Browser localStorage
- Browser sessionStorage
- Fetch API
- Existing HatchAI frontend utilities

DISCOURAGED:

- Large CSS frameworks
- Third-party charting libraries
- External font dependencies
- Large JavaScript utility packages
- Heavy icon libraries
- Excessive animations

NOT ALLOWED BY DEFAULT:

- React
- Next.js
- Angular
- Vue
- Tailwind runtime CDN
- Bootstrap JavaScript bundles
- Three.js
- WebGL-based dashboards
- Large animation libraries
- Node.js runtime dependencies
- Cloud-required UI components

These restrictions apply to the deployed interface.
Build-time tools may be considered if they produce
small, self-contained static assets.

---

## 4. Frontend Resource Budgets

Use the following initial optimization targets.

These are engineering budgets, not guaranteed
ESP32 hardware limits.

| Resource | Target |
|---|---|
| HTML per page | <= 30 KB |
| CSS total | <= 50 KB |
| JavaScript total | <= 80 KB |
| Individual image | <= 40 KB |
| Total deployed frontend | <= 350 KB |
| External runtime dependencies | 0 |
| Dashboard polling | >= 5 seconds |
| Simultaneous API polling | Minimize |
| Animated charts | Avoid by default |

Measure actual asset sizes after building.

Prefer smaller assets whenever possible.

Do not remove required functionality merely
to meet an arbitrary file-size target.

If a budget is exceeded:

1. Identify the reason.
2. Remove unnecessary code or assets.
3. Reuse shared styles and functions.
4. Optimize images and icons.
5. Report the remaining budget overrun.

## 5. UI Design Guidelines

UI UX Pro Max may choose:

- Colors
- Typography
- Spacing
- Card layouts
- Navigation
- Icons
- Responsive breakpoints
- Visual hierarchy
- Accessible interaction patterns

However, prefer:

- Clean dashboard layouts
- Simple cards
- Reusable CSS classes
- Minimal decorative elements
- System fonts
- Lightweight SVG icons
- Limited shadows
- Static backgrounds
- Clear status indicators

Avoid:

- Large background videos
- Particle effects
- Glassmorphism with extensive blur
- Animated gradients
- Continuous decorative animations
- Complex 3D visualizations
- Excessive nested elements

Use CSS rather than JavaScript for simple visual effects.

---

## 6. Animation Limiter

Animations must be lightweight and purposeful.

ALLOWED:

- Button hover transitions
- Simple opacity transitions
- Small transform effects
- Loading indicators
- Status changes
- Lightweight modal transitions

DEFAULT LIMITS:

- Transition duration: 100-250 ms
- No continuous decorative animation
- No unnecessary animation loops
- No repeated layout-triggering animations

Prefer:

```css
.button {
  transition: background-color 150ms ease,
              transform 150ms ease;
}

.button:hover {
  transform: translateY(-1px);
}

@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation: none !important;
    transition: none !important;
  }
}
```

Do not animate live temperature and humidity
readings unnecessarily.

Update displayed values only when data changes.

---

## 7. JavaScript Performance

Use vanilla JavaScript.

Rules:

1. Avoid unnecessary dependencies.
2. Cache frequently used DOM references.
3. Avoid rebuilding entire pages during polling.
4. Update only changed values.
5. Reuse existing event listeners.
6. Avoid repeated DOM queries in hot paths.
7. Avoid unnecessary timers.
8. Avoid duplicate API requests.
9. Prevent overlapping polling requests.
10. Stop unnecessary work on inactive pages.

Do not use continuous rendering loops for
ordinary dashboard widgets.

Avoid `requestAnimationFrame` loops unless
a specific animation requires them.

Use `textContent` for ordinary data updates.

Do not insert untrusted data using `innerHTML`.

---

## 8. API Request Limiter

HatchAI uses Arduino WebServer on port 80.

The ESP32 handles firmware control and HTTP
requests within its main-loop architecture.

Excessive requests can reduce responsiveness.

DEFAULT RULES:

- Dashboard polling: every 5 seconds
- Control-page polling: every 5 seconds
- Avoid duplicate requests for the same data
- Avoid overlapping requests
- Avoid aggressive automatic retries
- Do not poll every 100-500 milliseconds
- Do not introduce additional polling endpoints
  without a demonstrated need

Use the existing `espApi.js` utilities.

Prefer a shared response for multiple widgets.

When polling fails:

1. Show connection status.
2. Avoid tight retry loops.
3. Keep the last displayed data distinguishable
   from a fresh reading.
4. Resume polling using bounded retry behavior.

Do not represent stale readings as live readings.

---

## 9. JSON and Memory Limiter

The ESP32 constructs API responses using
limited device memory.

Do not request unnecessarily large JSON payloads.

Avoid:

- Large historical datasets in each response
- Redundant repeated fields
- Unbounded arrays
- Base64 images in JSON
- Large debug strings in production responses

Prefer:

- Existing API fields
- Bounded history arrays
- Small response objects
- Selective browser-side processing

Do not modify API schemas without reviewing
the firmware and all dependent frontend pages.

Browser RAM and ESP32 RAM are separate.

Client-side rendering does not directly consume
ESP32 heap, but large HTTP responses and
server-side response construction can.

---

## 10. Chart Limiter

HatchAI currently uses HTML Canvas for charts.

Keep this approach unless there is a clear
technical reason to change it.

Rules:

- No Chart.js by default
- No D3.js by default
- No continuous chart animation
- Reuse existing Canvas elements
- Redraw only when necessary
- Limit displayed data points
- Avoid unnecessary gradients and effects
- Handle browser resize efficiently

Existing history groups have bounded sizes.

Do not describe the existing hour, day, week,
and month groups as complete historical archives.

The current firmware does not reconstruct
long-term chart history from SD card CSV logs.

---

## 11. Asset and SPIFFS Limiter

All deployed frontend assets must remain
compatible with ESP32 SPIFFS.

Rules:

1. Prefer static HTML, CSS, and JavaScript.
2. Minimize image sizes.
3. Prefer SVG for simple icons.
4. Avoid large font files.
5. Avoid unnecessary duplicated assets.
6. Keep filenames and paths compatible
   with existing static-file routes.
7. Check SPIFFS partition capacity.
8. Build the filesystem image after changes.

Preferred image formats:

- SVG for simple icons
- WebP for suitable raster images
- Optimized PNG when transparency is needed

Do not add large decorative images
without checking the filesystem budget.

---

## 12. Responsive Design

Support:

- Mobile phones
- Tablets
- Desktop browsers

Prefer CSS Grid and Flexbox.

Use a mobile-first layout when appropriate.

Avoid generating separate large frontend
implementations for different screen sizes.

Keep controls usable on touchscreens.

Maintain readable text and sufficient contrast.

Use responsive layouts without excessive
JavaScript-based viewport calculations.

---

## 13. HatchAI Page Restrictions

### Dashboard

Prioritize:

- Temperature
- Humidity
- Heater status
- Fan status
- Egg-turner status
- Sensor status
- Active batch
- Hatch prediction
- Recent history chart

Avoid unnecessary decorative widgets.

### Control Page

Prioritize:

- Automatic/manual mode
- Heater controls
- Fan control
- Turner control
- Temperature target
- Humidity target
- Turning interval

Controls must clearly distinguish current
device state from requested state.

Do not change relay behavior through UI styling.

### Batch Page

Keep batch records compatible with
existing browser localStorage.

Do not introduce server-side batch storage
without an explicit backend implementation.

### Settings Page

Preserve:

- Account settings
- Wi-Fi management
- Existing calibration form behavior

Do not claim calibration offsets affect
firmware readings unless that functionality
has actually been implemented.

### Log Page

Do not invent functional log retrieval
or CSV download features.

The current page contains placeholder behavior.

Any new logging UI must match real API support.

---

## 14. Security and Safety

The UI must not be treated as the sole
security boundary.

Rules:

- Never expose credentials in UI logs.
- Avoid unsafe HTML injection.
- Validate browser inputs.
- Do not assume hidden buttons secure API routes.
- Do not bypass existing session workflows.
- Do not introduce unauthorized control paths.
- Avoid displaying false hardware states.

Backend authorization must be enforced
by firmware, not merely by frontend controls.

## 16. UI UX Pro Max Integration

When UI UX Pro Max is invoked:

STEP 1:
Generate a suitable visual design.

STEP 2:
Evaluate the proposed interface against
ESP32 resource and compatibility constraints.

STEP 3:
Remove unnecessary dependencies, effects,
and oversized assets.

STEP 4:
Implement using lightweight static assets.

STEP 5:
Preserve existing HatchAI API behavior.

STEP 6:
Measure asset sizes and inspect request patterns.

STEP 7:
Build the SPIFFS image when tooling is available.

STEP 8:
Report resource usage and remaining limitations.

If a visual feature is too expensive,
replace it with a simpler alternative
that preserves the intended user experience.

Do not sacrifice clarity, accessibility,
or functionality solely to reduce file size.

## 17. Expected Agent Output

After UI development or review, report:

### Design Summary
Describe the visual changes.

### Files Changed
List modified frontend files.

### Resource Budget
Report measured HTML, CSS, JavaScript,
image, and total asset sizes.

### Performance Review
Describe polling, rendering, and
dependency implications.

### Compatibility
Confirm which existing API contracts
and browser storage behaviors were preserved.

### Verification
List builds, browser tests, and
hardware tests actually performed.

### Remaining Issues
Identify unverified assumptions or
resource-budget exceptions.

---

## 18. Definition of Done

A UI task is complete when:

1. The requested design is implemented.
2. The frontend uses supported technologies.
3. Asset budgets are checked.
4. SPIFFS compatibility is reviewed.
5. HTTP polling remains bounded.
6. No unnecessary dependencies are introduced.
7. Existing APIs remain compatible.
8. Hardware control behavior is preserved.
9. Mobile and desktop layouts are usable.
10. Testing results and limitations are reported.

FINAL RULE:

Use UI UX Pro Max for design quality.

Use ESP32 UI Limiter for implementation constraints.

The final interface must be visually polished,
lightweight, reliable, and suitable for HatchAI's
ESP32-hosted web dashboard.
